# 提示词工程与模型选型

这个项目的提示词有三个，不是一个大提示词：**生成**、**自检**、**判定**。
拆开的原因是它们的目标冲突——生成要发散（想清楚表关系），自检要收敛（找错），
判定要保守（宁可拒答）。合在一起会让模型在"该自信"和"该怀疑"之间摇摆。

## 一、生成提示词的结构

固定的五段，顺序不能换：

1. **角色与边界**：一句话说清"你是数据分析助手，只输出 SQL"。
2. **输出约定**：从 `defaults.yml` 渲染出来的行数、小数位、最小样本量。
   这一段的特殊之处是它**由配置生成而不是手写**，所以改口径只改一处，
   而且能被测试断言"模型确实收到了这个数"。
3. **候选表卡**：检索出来的 2-4 张表，每张只带相关列，不带全表。
   带全表会让模型在 84 个字段里挑，选错列的概率显著上升。
4. **范例**：2-3 条 few-shot，按问题的「能力类型」匹配，不按文本相似度匹配。
5. **问题**：原样放入，不做改写。

一个反直觉的发现：**范例越相似越好，但不相似比没有更糟**。
早期做法是按 BM25 相似度取 top-3 范例，结果"渠道 ROI"这类题会匹配到
"渠道点击量"的范例，模型照着范例的列结构硬套，错得很自信。
后来改成按能力类型（计数 / 排名 / 同比 / 分组对比 / 明细）匹配，问题消失。

## 二、自检提示词

自检只做四件事，顺序固定：

- 表名和列名是否都在候选表卡里（这是幻觉的主要来源）
- 时间字段是否用了 `pay_time` 而不是下单时间
- 聚合是否漏了 `DISTINCT`（订单数、UV）
- 有没有忘记 `is_valid=1`

四条都是"能机械判断"的，刻意不放"业务逻辑对不对"这种需要领域知识的问题。
让模型自检业务逻辑，它会自信地说"没问题"。

## 三、判定提示词

判定器回答一个问题：**给定的证据是否足以回答问题**。

关键设计是"先摘录再判定"：要求模型先从证据里逐字摘录一句支撑回答的原文，
再判定是否充分；摘不出来就输出 `NONE`，强制走拒答。

这一步把误拒率从 20% 降到了 0%。原因不复杂：直接让模型输出 yes/no 时，
它会受问题措辞影响（问得越"专业"越容易说够）；要求它先摘录，
相当于逼它去证据里找锚点，找不到就自然说不够。

摘录出来的句子还会被塞进作答提示词当锚点。这一步解决的是另一个问题：
作答模型看到上万字证据时容易自我否定，说"根据提供的资料无法确定"，
而判定器明明已经确认够了。给它一句原文，它就不犹豫了。

## 四、温度

生成、自检、判定三处全部 `temperature=0`。没有例外。

这不只是为了稳定。实测 `temperature=0.7` 时，同一问题的 SQL 有 12% 概率
换个写法（子查询改 join、别名不同），结果集一样但 trace 里比对不上，
排查时会误以为"模型不稳定"。

## 五、模型选型

| 模型 | 40 题 EX | 单题成本 | 单题耗时 | 结论 |
|---|---|---|---|---|
| deepseek-chat | 90.0% | 0.026 元 | 9.2s | 默认 |
| deepseek-chat（非思考） | 90.0% | 0.026 元 | 9.2s | 同上 |
| 小参数模型 | 73.3% | 0.004 元 | 2.1s | 只够做 naive 兜底 |
| 规则基线 | 40.0% | 0 元 | 0.05s | 无 Key 时降级 |

选型没有做大规模横评，两个原因：一是预算，二是换模型要重跑全部消融，
而消融结论本身对模型敏感（`mix` 比 `naive` 差这个现象在小模型上不出现）。
所以这里的数字只对本项目这套提示词成立，不能外推。

## 六、一个失败过的尝试

试过让模型在生成 SQL 之前先输出"取数计划"（用哪张表、哪个指标、哪个时间字段），
再根据计划生成 SQL。理论上这能减少选错指标，实测 EX 从 90% 掉到 83.3%。

失败原因看 trace 很清楚：模型写的计划是对的，但它生成 SQL 时会"忘记"计划，
凭语感直接写。两段式提示词没有强制约束，中间产物就被丢了。
要让它生效，得把计划做成结构化输出并作为下一段的强输入，那是另一套工程，
当时没做。
