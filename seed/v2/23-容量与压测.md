# 容量与压测

压测环境：单机 8 核 16G，SQLite 只读快照 3.4 GB，embedding 本地 CPU，
LLM 走云端（网络往返约 600ms）。

## 一、单请求耗时拆解（full 模式，40 题均值）

| 阶段 | 耗时 | 占比 | 说明 |
|---|---|---|---|
| 检索 | 0.41s | 4% | BM25 + 向量，top_k=6 |
| 重排 | 1.2s | 13% | 20 候选重排到 6，模型常驻 |
| 生成 SQL | 3.9s | 42% | 上游 LLM，输出约 180 token |
| 执行 | 0.08s | 1% | 聚合查询，走索引 |
| 自检 | 2.1s | 23% | 一次 LLM 调用 |
| 判定 + 作答 | 1.5s | 16% | 两次调用合并 |
| 合计 | 9.2s | 100% | p50 |

结论：**模型调用占 81%**，本机优化空间很小。要降延迟只能减调用次数或换更快的模型。

## 二、并发表现

| 并发 | QPS | p50 | p99 | 错误率 |
|---|---|---|---|---|
| 1 | 0.11 | 9.2s | 9.4s | 0% |
| 4 | 0.42 | 9.6s | 11.2s | 0% |
| 8 | 0.78 | 10.4s | 14.1s | 0.3% |
| 16 | 1.02 | 16.8s | 28.4s | 4.1% |
| 32 | 1.05 | 31.2s | 52.6s | 12.8% |

拐点在 8 并发。再往上 QPS 不再涨，只是排队变长、超时变多。
瓶颈不是 CPU 也不是数据库，是上游 LLM 的连接数限制和本地的信号量闸门。

## 三、naive 模式

| 并发 | QPS | p50 |
|---|---|---|
| 8 | 6.4 | 1.1s |
| 32 | 7.1 | 4.2s |

naive 只调一次 LLM，延迟降一个数量级，代价是 EX 从 90% 掉到 80%。
生产上按问题复杂度分流：能命中指标卡且单表的走 naive，其余走 full。
分流后平均延迟 3.1s，EX 保持 88% 左右（有 2 道题在分流判定上出错）。

## 四、内存

| 组件 | 常驻内存 |
|---|---|
| Python + FastAPI | 180 MB |
| embedding（bge-small-zh） | 210 MB |
| 重排（bge-reranker-int8） | 340 MB |
| SQLite 页缓存 | 256 MB |
| 峰值（索引期） | 1.4 GB |

索引期内存峰值来自向量矩阵，100 块 × 512 维 × 4 字节只有 200 KB，
大头其实是实体关系的图结构反序列化。

## 五、容量上限

单实例的经验上限：

- 语料 500 块以内，检索延迟线性增长可接受（每 100 块 +35ms）
- 实体超过 2 万时，图查询开始明显变慢（Neo4j 之外的内存图实现都会这样）
- SQLite 事实表 5000 万行以内聚合查询在 100ms 级，再大要换列存

超出这些值不是"跑不动"，是"慢到需要重新设计"。当前部署规模离上限还很远，
所以没有做分片。
