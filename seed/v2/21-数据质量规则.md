# 数据质量校验规则

30 条规则，分「阻塞」和「告警」两级。阻塞级当天数据不进仓库，告警级进但打标。

为什么分级：全阻塞会让上游一次小故障卡住整个链路，全告警又等于没有约束。
分级的判据是「错了会不会让指标失去意义」——订单号为空会，分类数变化不会。


| 编号 | 规则 | 校验方式 | 级别 | 为什么在意 |
|---|---|---|---|---|
| Q01 | fact_order.order_id 非空 | COUNT(*) WHERE order_id IS NULL = 0 | 阻塞 | 订单无号不可追溯 |
| Q02 | fact_order.pay_amount >= 0 | 无负值（退款另表记录） | 阻塞 | 负金额通常是冲正未单独建行 |
| Q03 | order 状态在枚举内 | status IN (paid,shipped,done,refunding,refunded,closed) | 阻塞 | 新增状态未同步会导致 GMV 漏算 |
| Q04 | 同 order_id 的 pay_time 一致 | 按 order_id 分组后 COUNT(DISTINCT pay_time) = 1 | 告警 | 不一致说明拆行时时间取错 |
| Q05 | qty > 0 且 <= 99 | 区间校验 | 告警 | 异常大额通常是测试单 |
| Q06 | book_id 外键存在 | LEFT JOIN dim_book WHERE b.book_id IS NULL = 0 | 阻塞 | 悬空外键会让 join 静默丢行 |
| Q07 | user_id 外键存在 | 同上 | 告警 | 注销用户的历史数据允许悬空 |
| Q08 | stat_date 与 pay_time 同日 | date(pay_time) = stat_date | 阻塞 | 不一致会让日报和明细对不上 |
| Q09 | fact_click.event_type 在枚举内 | impression / click | 阻塞 | 废弃的 view 会污染 CTR 分母 |
| Q10 | fact_click.device_id 非空 | 空值率 < 0.1% | 阻塞 | UV 依赖它，空值直接低估 |
| Q11 | fact_rating.score 在 1-10 | 区间 + 0.5 步长校验 | 阻塞 | 越界值会拉偏均分 |
| Q12 | fact_rating 同用户同书同日唯一 | 重复视为重复提交，置 is_valid=0 | 告警 | 重复提交是刷分的主要形态 |
| Q13 | dim_book.list_price > 0 | 无零价与负价 | 阻塞 | 零价书会让折扣深度爆表 |
| Q14 | dim_book.rating_avg 与明细一致 | 抽样 100 本对比 AVG(score) | 告警 | 每夜重算失败会保留旧值 |
| Q15 | dim_book.rating_cnt 与明细一致 | 同上 | 告警 | 同上 |
| Q16 | dim_date 覆盖范围完整 | 2019-01-01 至 2027-12-31 无缺日 | 阻塞 | 缺日会让补齐逻辑跳空 |
| Q17 | dim_category 无环 | parent_id 链路深度 <= 2 | 阻塞 | 环会导致树遍历死循环 |
| Q18 | 一级分类数 = 18 | level=1 的行数 | 告警 | 重构期间会临时变化 |
| Q19 | dim_channel.channel_id=0 存在 | 自然流量必须有独立 id | 阻塞 | 缺失会让自然流量被当成 NULL 丢掉 |
| Q20 | 付费渠道 unit_price > 0 | is_paid=1 时校验 | 告警 | 零单价通常是合同未录入 |
| Q21 | bridge_book_tag 无重复组合 | GROUP BY book_id,tag HAVING COUNT(*)>1 = 0 | 阻塞 | 重复会放大关联后的金额 |
| Q22 | 标签 end_date >= start_date | 区间校验 | 阻塞 | 反序会让标签永远不生效 |
| Q23 | dim_author.country 非空 | 空值填「未知」 | 告警 | NULL 会在分组时被丢掉 |
| Q24 | dim_publisher 同名不同 id 检出 | GROUP BY publisher_name HAVING COUNT(DISTINCT publisher_id)>1 | 告警 | 跨省同名是已知问题，需人工确认 |
| Q25 | GMV 日环比突变检测 | |今日-昨日|/昨日 > 50% 告警 | 告警 | 突变多为口径或上游故障 |
| Q26 | 订单数去重前后差异 | COUNT(*) / COUNT(DISTINCT order_id) 应在 1.2~1.4 | 告警 | 偏离说明拆行规则变了 |
| Q27 | 退款率区间 | 0% ~ 15% | 告警 | 越界多为状态机异常 |
| Q28 | CTR 区间 | 0.5% ~ 25% | 告警 | 越界多为曝光未上报 |
| Q29 | UV <= PV | 按日校验 | 阻塞 | 反过来一定是去重键错了 |
| Q30 | 事实表分区无重叠 | stat_date 分区互斥 | 阻塞 | 重叠会导致重复计算 |

## 校验跑在哪一步

校验在快照生成之后、索引重建之前，顺序不能反。原因是：索引一旦建好，
错误数据会被固化成实体和关系，改数据不会自动改索引，只能重建——
那是一次实打实的成本。所以宁可让校验卡住索引。

## 三条例外

**Q07 只告警不阻塞**。注销用户的历史订单仍然要保留，外键悬空是正常状态。
如果按阻塞处理，每个注销用户都会卡住整批数据。

**Q14/Q15 是抽样不是全量**。逐本对比 `rating_avg` 和明细平均要扫 286 万行，
在 T+1 窗口里来不及。抽 100 本，容差 0.01 分，命中率够用。

**Q25 的 50% 阈值是拍出来的**。没有统计依据，是根据历史事故的经验值。
它的作用是"提醒人看一眼"，不是"判定数据错了"，所以别把它当硬门禁。
