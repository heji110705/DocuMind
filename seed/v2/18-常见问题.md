# 常见问题

按提问频率排序，不按文档结构排序。答案里出现的数字都是实测值，不是估算——
凡是写"约"的地方，是因为跨语料规模会有浮动，不是没测过。


## 口径

### 问：订单数为什么要去重？不去重会差多少？

`fact_order` 的粒度是一单一书一行，一个订单买三本书就是三行。直接 `COUNT(*)` 得到的是订单行数，实测比真实订单数高 28%。所以订单数一律 `COUNT(DISTINCT order_id)`，客单价的分母也用这个值。行数本身有用（算平均每单几本书），但它的名字叫 `order_line_cnt`，不叫订单数。

### 问：GMV 到底含不含退款？

分两个指标。`gmv_gross` 含退款，是运营看板的默认值；`gmv_net` 扣掉已退款订单。注意 `refunding`（退款中）两个指标都算进去，只有 `refunded` 才从净额里扣。对外汇报如果只说「GMV」，默认指 `gmv_gross`，但最好把口径写出来。

### 问：为什么站内评分不能和豆瓣评分一起算？

三个原因：样本不同（站内是购买用户，豆瓣是全网）、量纲虽同为 10 分制但分布不同、覆盖不同（豆瓣有 11% 的书为空）。把两者求平均得到的数没有业务含义。如果要做「站内评分相对豆瓣评分的偏移」，那是一个差值指标，需要显式过滤空值后再算。

### 问：DAU 为什么用 device_id 而不是 user_id？

31% 的曝光和点击事件没有登录态，`user_id` 为 NULL。聚合函数会自动忽略 NULL，用 `COUNT(DISTINCT user_id)` 算出来的 DAU 会低三成左右。代价是换机、清缓存会被算成新用户，所以 DAU 天然略高于真实人数，这是行业通行做法。

### 问：CTR 的分母是什么？

曝光事件数，即 `COUNT(*) WHERE event_type = 'impression'`。分子是 `SUM(is_click)`。分母必须显式限定 `event_type`，因为 2023 年的数据里残留了已废弃的 `view` 类型，不限定会把分母撑大。

### 问：退款率的分母包不包括未支付的关闭单？

不包括。分母是支付成功的订单，即 `status IN ('paid','shipped','done','refunding','refunded')`。如果把 `closed` 也算进分母，退款率会被系统性低估约 4 个百分点——2026-03 修正过一次，修正后退款率整体上浮。

### 问：ARPU 和 ARPPU 差在哪？

分母差一个「是否付费」。ARPU = GMV / 全部活跃用户，ARPPU = GMV / 付费用户。ARPU 用来看整体变现效率，ARPPU 用来看付费用户的钱包深度。两者恒有 ARPPU > ARPU，把它们的曲线放一张图里比较没有意义。

### 问：7 日留存是「第 7 天」还是「7 天内」？

是第 7 天当天活跃，日历日 D+7，不是 7 天内任意一天。后者的数值会高很多，且随窗口定义变化极大。本项目统一用 D+7 当天口径，需要「7 天内」时会显式写成 `retention_7d_cum`，不叫留存。

### 问：ISO 周为什么会切出 53 周？

ISO 8601 的周归属按周四所在年计算，年末几天可能属于次年第 1 周。所以按自然年 `year` + `iso_week` 分组时，某些年份会出现一个只有 2-3 天的「第 53 周」。周同比必须用 `iso_year` + `iso_week`，不能用 `year` + `iso_week`。

### 问：定价和成交价差多少？

实测 `list_price` 乘数量得到的金额，比实际 `pay_amount` 高 18%~25%。差额来自券、活动价、会员价，还有运费的反向影响（满 99 包邮会拉低差额比例）。任何涉及金额的分析一律用 `pay_amount`，`list_price` 只在算折扣深度时作为分母。

### 问：优惠金额为什么不能和实付相加？

因为 `pay_amount` 已经是扣除优惠后的金额，`discount_amount` 是差额本身。正确的关系是 `list_amount - discount_amount + freight = pay_amount`。把优惠和实付相加得到的是「原价 + 运费 + 优惠」这种无意义的值。

### 问：新书上架数按哪个日期算？

按 `launch_date`（站内上架日），不是 `publish_date`（首次出版日）。引进版的书首版日期可能是十几年前，按出版日算会把它们全部推到旧年份，「本月新书」直接归零。

### 问：评论数和评分数的关系？

评论数 ≤ 评分数。一条评分可以不带文字，`has_comment=0`。评论率 = `SUM(has_comment) / COUNT(*)`，两者都限定 `is_valid=1`。常见的错是把评论数当评分人数，或者拿评论数除以订单数（分母都不对）。

### 问：渠道 ROI 为什么不能对自然流量算？

自然流量没有成本分母，除法无定义。计算 ROI 时 `is_paid=0` 的渠道必须排除，分子分母都要排除——只排除分母会让自然流量以「零成本高 ROI」的形式霸榜。

### 问：「销量」和「订单数」差多远？

销量是 `SUM(qty)`（册数），订单数是去重订单数。一单平均 1.6 本左右，所以销量约等于订单数的 1.6 倍，但两者含义完全不同：销量看货，订单看人。统计销量时还要排除赠品（`book_id < 0`）。


## 能力

### 问：为什么有的问题会被拒答？

检索到的证据不足以支撑回答时，判定器会输出 `NONE` 锚点，产品返回拒答（HTTP 200，`refused=true`，错误码 E1080）。这是正确行为不是故障。拒答率在评测里是单独一个指标，误答比拒答严重得多，所以阈值偏保守。

### 问：能不能查实时数据？

不能。埋点延迟最长 6 小时，仓库是 T+1 的日粒度快照。文档里出现「实时看板」的地方，实际含义都是当日数据次日可见。要看秒级数据得接实时数仓，本项目没有做。

### 问：能不能直接写 SQL 让它执行？

接口不提供这个入口。用户只能提自然语言问题，SQL 由系统生成并通过安全校验。管理员有 `/v1/admin/explain` 可以只校验不执行，用于排查 E1061，但它也不能执行。

### 问：支持多轮追问吗？

支持，会话 24 小时过期。追问时上一轮的 SQL 和指标会作为上下文带进来，所以「那上个月呢？」能正确继承筛选条件。超过 24 小时后会话失效，需要重新提问。

### 问：能导出 Excel 吗？

接口返回结构化 `rows`，导出由客户端做，服务端不生成文件。这样做的原因是服务端写文件会引入清理、并发、权限三类问题，而前端拿到 rows 之后导出只是一行代码。

### 问：能回答「为什么」类的问题吗？

不能给出因果结论，只能给数据。问「为什么 5 月销量降了」，系统会返回按维度拆解的数据（渠道、分类、新老客），由人判断原因。任何看起来像因果的句子都不会被生成。

### 问：图表是模型画的吗？

不是。模型只产出数据，图表由服务端按固定规则渲染成 SVG。选型规则很朴素：时间序列折线、分类对比柱状、占比饼图，超过 12 个分类强制转柱状。这样做的目的是可预测——同一个结果永远得到同一张图，录屏和回归测试都能用。

### 问：没配 LLM Key 能跑吗？

能，会降级到规则基线：关键词匹配语义卡，直接拼出 SQL。能力弱（只能处理计数、求和这类简单问题），但全链路可跑、零成本，适合演示和 CI。

### 问：能处理 PDF 吗？

可以，接入层用 PyMuPDF 做版面解析（标题层级按字号+加粗推断，表格用 `find_tables` 抽取），再交给同一个检索管线。扫描件需要先 OCR，本项目没有内置 OCR。

### 问：支持哪些数据库？

当前只支持 SQLite 只读快照。`Repo` 协议隔离了访问层，换 PostgreSQL 只需实现一个新类，但 SQL 方言校验（sqlglot 的 dialect 参数）和只读机制要跟着改，不是零成本。


## 部署

### 问：本地怎么起？

三步：`pip install -r requirements.txt`、复制 `.env.example` 为 `.env` 填 Key、`python -m uvicorn app.main:app --port 8000`。首次跑要建索引（`python run_index.py`），之后直接起服务即可，索引落在 `rag_storage/`。

### 问：为什么索引要单独跑，不放在启动里？

索引会调几十到几百次 LLM，耗时几分钟到几十分钟，放在启动里会让健康检查超时、容器反复重启。而且索引是幂等的重活，重启服务不该重跑它。

### 问：数据快照放哪？

`data/warehouse.sqlite`，只读打开。这个文件不在版本控制里（体积大且含业务数据），由 `make snapshot` 从上游导出。缺失时 `/readyz` 返回 503 和 E1090。

### 问：容器镜像多大？

约 1.2 GB。大头是 onnxruntime 和 embedding 模型（bge-small-zh 约 90 MB）。如果改用云端 embedding，可以省掉 onnxruntime，镜像降到 400 MB 左右，代价是每次查询多一次网络往返和 embedding 费用。

### 问：能离线跑吗？

不完全能。生成 SQL 必须调 LLM（规则基线除外），所以断网时只有降级模式可用。本地 embedding 是离线的，重排模型也是离线的。

### 问：端口被占用怎么办？

换端口：`--port 8001`。默认 8000 是因为和常见前端 dev server 的 3000/5173 不冲突。如果一定要 8000，先 `netstat -ano | findstr :8000` 找进程。

### 问：怎么改语义层配置？

改 `data/semantic/*.yml` 后调 `/v1/admin/reload` 热重载，不用重启。校验失败时保留旧配置并返回 E1030，不会出现「配置改坏了服务起不来」的情况。

### 问：日志在哪？

标准输出（JSON 行格式），由容器运行时收集。trace 单独落 `traces.sqlite`，保留 7 天。两者分工：日志回答「服务是否正常」，trace 回答「这一次为什么答错」。

### 问：怎么备份？

要备的只有两样：`data/semantic/` 配置和 `traces.sqlite`。索引可重建（花钱即可），快照可从上游再导，都不需要备份。

### 问：能多实例部署吗？

只读查询可以。写的地方只有 trace 和 feedback，SQLite 并发写会锁，多实例要换成 PostgreSQL 或把写操作打到一个独立服务。当前默认单实例。


## 成本

### 问：一次问答花多少钱？

`full` 模式约 0.026 元，`mix_rr` 约 0.019 元，`naive` 约 0.004 元。差距来自链路长度：full 要检索、生成、自检、判定四步，naive 只生成一次。以上按 deepseek-chat 的低峰单价算，高峰会贵一倍左右。

### 问：建一次索引多少钱？

6 万字规模的语料约 0.9 元。算法是：字数换算 token 约乘 0.6，每块 1200 token、每块调 2 次 LLM（初始抽取 + 1 轮 gleaning），单次输入约 1.5k token。真正贵的是反复重建——全量重建 20 次就是 18 元左右。

### 问：哪一步最贵？

实体关系抽取。它占索引成本的 90% 以上，因为每块都要把全文喂进去让模型抽实体。embedding 反而便宜到可以忽略（本地模型零成本，云端也是千 token 几厘钱）。

### 问：怎么降成本？

四个有效手段，按性价比排序：一是关掉 gleaning（省 50% 调用，实体少 3%、关系少 27%）；二是不要反复全量重建索引，改为增量插入；三是查询期用 `naive` 兜底简单问题；四是重排只对 top-20 候选做，不要对全量做。

### 问：gleaning 到底值不值？

不值得默认开。实测开一轮 gleaning 让调用翻倍、成本涨 65%，换来实体少 3%、关系多 27%，而评测分数没有显著变化。关系多听起来是好事，但多出来的多半是弱关系，反而稀释检索。

### 问：缓存能省多少？

同一语料重复索引时，LLM 响应缓存能命中大部分抽取调用，成本接近零。查询期的缓存命中率低（问法几乎不重复），只有完全一样的问题才命中。

### 问：为什么 embedding 用本地的？

云端 embedding 每百万 token 几毛钱，按本项目规模一年也就几十块，钱不是问题。换本地是因为云端要开通模型权限、要处理限流，而本地模型 90 MB、CPU 10ms 一条，离线可跑、零配置。等规模上来了再换云端，接口已经抽象好了。

### 问：预算怎么估？

按「日活问题数 × 0.03 元」估，再乘 1.5 的安全系数。1000 问/天约 45 元/天、1350 元/月。索引重建单独算，一次约 1 元。


## 排查

### 问：报 E1061 怎么办？

说明 SQL 被安全策略拒绝。先用 `/v1/admin/explain` 传进去看 `reasons`，常见三种：引用了未声明的表（换个问法或补表卡）、命中了敏感列、跨租户表前缀。不要改安全规则来绕过，先确认是不是语义卡缺东西。

### 问：报 E1052 上下文超长怎么办？

先看 `top_k`，默认 6，调到 4 试试。再检查 fewshots 的 tags 是否命中过多（一次拼进 20 条范例很容易撑爆）。最后才怀疑模型窗口——32k 的窗口一般够用。

### 问：报 E1072 扫描行数超限怎么办？

不是结果太多，是过滤条件没走索引。看 `EXPLAIN QUERY PLAN` 里有没有 `SCAN`，常见原因是 `date_key` 用了字符串比较、或者 `LIKE '%xx%'` 前置通配。

### 问：答案对但数字不对，先查什么？

按这个顺序：一查是不是没加 `is_valid=1`（评分类）；二查订单数有没有去重；三查 UV 用的是不是 `user_id`；四查时间用的是 `pay_time` 还是下单时间。这四条覆盖了历史工单的绝大多数。

### 问：为什么同一问题两次结果不同？

生成 SQL 用 `temperature=0`，理论上稳定。不稳定的来源通常是：检索 top_k 边界上分数接近导致排序抖动、或者会话里带了上一轮上下文。复现时把 `session_id` 清掉再试。

### 问：SQL 里出现了不存在的表名，怎么回事？

模型幻觉。安全规则 G03 会挡住并返回 E1031，不会真的执行。频发的话说明语义卡的 `meaning` 写得太抽象，模型猜不到该用哪张表，把业务含义写具体一点通常能压下去。

### 问：结果为空但应该是有的？

三个常见原因：时间字段用了 NULL（未支付订单的 `stat_date` 为空）；过滤了 `is_active=1` 但目标书已下架；分类用了二级 `category_id` 却按一级过滤。先把 WHERE 条件逐条去掉，看哪一条把它过滤没的。

### 问：重排很慢，第一次要 20 多秒？

首次调用把模型加载时间算进了请求耗时。解决办法是启动时预热跑一次空推理，并把送入重排的文本截断到 512 字符。改完之后稳定在 5.9 秒/题。

### 问：服务起来了但 /readyz 一直 503？

看返回体里的 `warehouse` 和 `semantic` 字段。`warehouse` 失败是快照缺失或损坏，`semantic` 失败是 YAML 校验没过。两者都不会自动修复，要修数据或改配置。

### 问：索引跑到一半断了怎么办？

断点不会自动续。要么清空 `rag_storage/<tag>/` 重跑，要么用 `ainsert` 单文档插入，已完成的文档不会重复扣费（响应缓存在）。别直接重跑全量——会重复计费。


## 评测

### 问：90% 这个数是怎么算的？

40 道题里 30 道可答、10 道必拒。90.0% 指可答题中结果集完全一致的比例（27/30）。拒答正确率单独算，是 100%（10/10）。两个数不混着报，也不加权平均。

### 问：为什么用结果集比对，不用 SQL 字符串比对？

同一个问题有多条正确 SQL（列顺序、别名、是否用子查询）。字符串比对会把对的判错。结果集比对允许列顺序不同，但值必须完全一致、行数必须一致。

### 问：评测会不会过拟合？

会，而且这是这类项目最大的诚实性问题。缓解手段有三：一是题目按能力类型分层，不是按文档段落找；二是留一部分题只在最终跑一次，不参与调参；三是把失败清单全部公开，包括修不好的。

### 问：为什么不用 LLM 当裁判？

不稳定且不可复现。同一个答案两次判定可能不同，而且裁判本身会偏向啰嗦的答案。字符串关键词判定虽然粗糙，但它是确定的：同一份答案永远得同一个分。

### 问：拒答题怎么判？

判 `refused=true` 即正确。如果模型硬答了（`refused=false`），无论答案多合理都算错——因为这类题的设计意图就是「文档里没有，应该承认不知道」。

### 问：消融的四个配置分别是什么？

`naive` 只有生成；`mix` 加检索；`mix_rr` 再加重排；`full` 再加自检与证据判定。实测 `naive` 80.0%、`mix` 76.7%、`mix_rr` 90.0%、`full` 90.0%。`mix` 反而比 `naive` 低，是因为检索带进来的干扰块让模型选错了指标。

### 问：1 题值多少个百分点？

30 道可答题里，1 题 = 3.3 个百分点。这个粒度太粗，所以 90% 和 86.7% 的差距其实只有 1 道题。结论要谨慎表述，扩到 120 题后 1 题才降到 0.83 个百分点。


## 还有一类问题没有答案

上面 60 条都有一个确定答案。实际工单里还有一类问的是"你们这个准不准"，
它没有答案，只有口径：在 30 道可答题上结果集等价 90.0%，40 道题的拒答正确率 100%，
换成别的语料、别的业务域，这些数字都不成立。把这句话写在文档里，
比再补十条 FAQ 都有用。
