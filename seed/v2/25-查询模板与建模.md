# 查询模板与建模规范

12 个模板覆盖了实际提问的绝大多数形态。模板的作用不是让模型照抄，
而是让它在生成时有个"形状"可参照——尤其在比率、同比、留存这三类上，
模型自己发挥的错误率明显更高。

## 一、建模的三条硬规矩

**先定粒度，再写 SQL。** 每张表的粒度都写在字段字典的第一行。
`fact_order` 是"一单一书一行"，所以任何"订单数"都必须去重。
粒度没定就写聚合，错了也不会报错，只会静默给出一个偏大的数。

**维度表和事实表分开。** 维度表放属性（书名、分类、渠道），事实表放事件（评分、点击、订单）。
合并成一张宽表看起来省事，代价是任何一个属性变更都要回刷历史事实，而且事实表会膨胀十倍。

**不要在事实表里存派生指标。** 折扣深度、客单价这类都由 SQL 现算。
存下来就会有"存的值"和"算的值"两个版本，早晚对不上。
唯一的例外是 `dim_book.rating_avg`——它是每夜重算的快照，因为逐题实时算 286 万行太慢。
这个例外在字段字典里写明了。

## 二、12 个模板


### T01 单指标总量

适用：问「一共有多少」「总共多少」时用，不带分组。

```sql
SELECT COUNT(*) AS 在售书目数 FROM dim_book WHERE is_active = 1;
```


### T02 按维度分组排名

适用：问「TOP N」「哪几个最多」时用，必须带 LIMIT 和 ORDER BY。

```sql
SELECT c.channel_name AS 渠道, ROUND(SUM(o.pay_amount), 2) AS GMV
FROM fact_order o JOIN dim_channel c ON o.channel_id = c.channel_id
WHERE o.status <> 'closed' AND o.stat_date BETWEEN '2026-05-01' AND '2026-05-31'
GROUP BY c.channel_name ORDER BY GMV DESC LIMIT 10;
```


### T03 比率类

适用：分子分母分开聚合再相除，不要先算每行的比率再平均。

```sql
SELECT ROUND(100.0 * SUM(is_click) / COUNT(*), 2) AS CTR
FROM fact_click
WHERE event_type IN ('impression','click') AND stat_date = '2026-05-20';
```


### T04 同比

适用：用 dim_date 的 year 与 month 对齐，不要用自然语言算日期。

```sql
SELECT d.month AS 月份,
       ROUND(SUM(CASE WHEN d.year = 2026 THEN o.pay_amount END), 2) AS 今年,
       ROUND(SUM(CASE WHEN d.year = 2025 THEN o.pay_amount END), 2) AS 去年
FROM fact_order o JOIN dim_date d ON o.stat_date = d.full_date
WHERE o.status <> 'closed' AND d.month = 5 AND d.year IN (2025, 2026)
GROUP BY d.month;
```


### T05 环比

适用：用窗口函数对上一期取值，注意缺月要补零。

```sql
SELECT 月份, GMV,
       ROUND(100.0 * (GMV - LAG(GMV) OVER (ORDER BY 月份)) / LAG(GMV) OVER (ORDER BY 月份), 2) AS 环比
FROM (SELECT d.month AS 月份, SUM(o.pay_amount) AS GMV
      FROM fact_order o JOIN dim_date d ON o.stat_date = d.full_date
      WHERE o.status <> 'closed' AND d.year = 2026 GROUP BY d.month);
```


### T06 去重计数

适用：订单数、UV、付费用户都走这个模板，DISTINCT 不能漏。

```sql
SELECT COUNT(DISTINCT order_id) AS 订单数 FROM fact_order WHERE status <> 'closed';
```


### T07 条件聚合做交叉表

适用：一张表里同时出多个口径，避免跑多次查询。

```sql
SELECT d.month AS 月份,
       COUNT(DISTINCT CASE WHEN o.is_refund = 1 THEN o.order_id END) AS 退款单数,
       COUNT(DISTINCT o.order_id) AS 总单数
FROM fact_order o JOIN dim_date d ON o.stat_date = d.full_date
WHERE o.status <> 'closed' AND d.year = 2026 GROUP BY d.month;
```


### T08 分层聚合（先明细后汇总）

适用：需要「人均」时先按人聚合再平均，否则被高频用户带偏。

```sql
SELECT ROUND(AVG(amt), 2) AS 人均消费 FROM (
  SELECT user_id, SUM(pay_amount) AS amt FROM fact_order
  WHERE status <> 'closed' AND stat_date BETWEEN '2026-05-01' AND '2026-05-31'
  GROUP BY user_id);
```


### T09 留存（cohort）

适用：首访日 + D7 是否活跃，用自连接，不要用「7 天内」近似。

```sql
WITH first_seen AS (
  SELECT device_id, MIN(stat_date) AS d0 FROM fact_click GROUP BY device_id
)
SELECT COUNT(DISTINCT f.device_id) AS cohort,
       COUNT(DISTINCT c.device_id) AS d7_active
FROM first_seen f
LEFT JOIN fact_click c ON c.device_id = f.device_id
     AND c.stat_date = date(f.d0, '+7 day')
WHERE f.d0 = '2026-05-01';
```


### T10 明细查询

适用：带 LIMIT，列不要超过 8 个，否则前端渲染不下。

```sql
SELECT o.order_id AS 订单号, b.book_name AS 书名, o.qty AS 数量,
       ROUND(o.pay_amount, 2) AS 实付
FROM fact_order o JOIN dim_book b ON o.book_id = b.book_id
WHERE o.stat_date = '2026-05-20' AND o.status <> 'closed'
ORDER BY o.pay_amount DESC LIMIT 20;
```


### T11 空值处理

适用：比率的分母可能为 0，用 NULLIF 而不是 CASE。

```sql
SELECT ROUND(100.0 * SUM(is_click) / NULLIF(COUNT(*), 0), 2) AS CTR FROM fact_click;
```


### T12 中位数

适用：SQLite 没有 median，用窗口函数取中间位置。

```sql
SELECT AVG(amt) AS 中位数 FROM (
  SELECT amt, ROW_NUMBER() OVER (ORDER BY amt) AS rn, COUNT(*) OVER () AS n
  FROM (SELECT SUM(pay_amount) AS amt FROM fact_order WHERE status <> 'closed' GROUP BY user_id)
) WHERE rn IN ((n + 1) / 2, (n + 2) / 2);
```


## 三、三个模板里的常见错法

**T03 比率类**。很多人会写成 `AVG(is_click)`，看着也对——因为 `is_click` 是 0/1。
但一旦加了 `WHERE` 过滤掉部分曝光，`AVG` 的分母就变成了"过滤后的事件数"，
和 `SUM/COUNT` 的口径不再一致。两个写法在无过滤时等价，在有过滤时分道扬镳，
这种"有时对有时错"是最难排查的。

**T05 环比**。`LAG` 在缺月时会跨过空月取值，得到的是"上一个有数据的月"而不是"上个月"。
月度数据里 2 月常有异常，跨过去看起来数值合理，实际错位一个月。
所以模板里先按月聚合、再取 LAG，中间不做过滤。

**T09 留存**。用 `date(d0, '+7 day')` 精确到天。曾经用过 `BETWEEN d0+1 AND d0+7`，
那个口径叫"7 日内活跃"，数值通常高 30% 以上，且随窗口拉长趋近 100%，
完全失去区分度。
