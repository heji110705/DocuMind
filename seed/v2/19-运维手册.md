# 运维手册与故障处置

12 个真实发生过的场景。写法统一：现象 → 排查 → 处置 → 预防。
排查步骤按"最可能且最便宜"排序，不要一上来就看代码。


## R01　问答全部报 E1050（LLM 调用失败）

**现象**：问答全部报 E1050（LLM 调用失败）。

**排查**：1. `curl /healthz` 确认进程活着；2. 直接调上游 `/chat/completions`；3. 看 trace 里 `llm` span 的 status。

**处置**：上游 5xx 一般是对方故障，重试 3 次后降级到规则基线；401/403 是 Key 失效，换 Key 并重载。

**预防**：Key 过期前 7 天提醒；上游错误率 >5% 触发告警。


## R02　响应时间从 1s 涨到 10s+

**现象**：响应时间从 1s 涨到 10s+。

**排查**：1. 看 trace 里各 span 耗时占比；2. 确认是否切到了 full 模式；3. 看重排是否每次都在加载模型。

**处置**：重排模型应常驻内存，若每次重载是预热逻辑失效；full 模式本身就要 9-10s，属预期。

**预防**：给每个 span 设耗时预算，超预算打 warn。


## R03　全部问题都被拒答

**现象**：全部问题都被拒答。

**排查**：1. 看 E1080 的 ratio；2. 检查判定器提示词是否被改；3. 检查证据是否为空（检索挂了）。

**处置**：若证据为空但检索正常，是 embedding 维度不匹配导致相似度全为 0；核对 EMBEDDING_DIM。

**预防**：启动时自检：用一句已知文档里的句子做检索，命中率应为 100%。


## R04　DAU 突然翻倍

**现象**：DAU 突然翻倍。

**排查**：1. 查是否有重复上报（同一 device_id 同秒多条）；2. 查埋点版本是否重复初始化。

**处置**：去重键加上 event_id 的哈希；重复上报的数据按 event_id 去重后重算。

**预防**：埋点 SDK 加幂等校验，同一 event_id 24h 内丢弃。


## R05　订单数比业务系统少

**现象**：订单数比业务系统少。

**排查**：1. 对比时间口径（pay_time vs create_time）；2. 查是否过滤了 closed；3. 查是否漏了跨日支付。

**处置**：统一按 pay_time 归日；closed 只在算 GMV 时排除，算单量时看口径定义。

**预防**：每日与业务系统对账，差异 >0.5% 告警。


## R06　SQL 全部被 E1061 拒绝

**现象**：SQL 全部被 E1061 拒绝。

**排查**：1. `/v1/admin/explain` 看 reasons；2. 确认 tables.yml 是否加载成功。

**处置**：多是热重载失败但进程没报错——reload 返回 E1030 时旧配置仍在用，需修 YAML 后重载。

**预防**：reload 失败时打 ERROR 日志并在 /readyz 暴露。


## R07　查询报 database is locked

**现象**：查询报 database is locked。

**排查**：1. 看是否有写操作（trace / feedback）；2. 看并发数是否超过 8。

**处置**：写操作串行化到一个连接；读用独立只读连接。SQLite 的 WAL 模式能显著缓解。

**预防**：读写分离连接池；写操作加超时 3s。


## R08　容器反复重启

**现象**：容器反复重启。

**排查**：1. 看退出码（137=OOM，1=启动异常）；2. 看是否在启动时建索引。

**处置**：建索引移到 initContainer 或独立任务；内存不够时把 embedding 的 batch 降到 8。

**预防**：启动时只做校验不做重活，健康检查起始延迟 30s。


## R09　引用编号和原文对不上

**现象**：引用编号和原文对不上。

**排查**：1. 取 trace 里的 citations；2. 对比 chunk_id 与证据块编号的映射。

**处置**：证据块编号必须在拼提示词时生成并随 trace 落盘，事后重新编号必然错位。

**预防**：编号生成与引用解析用同一个函数，加单测断言。


## R10　同一问题答案时好时坏

**现象**：同一问题答案时好时坏。

**排查**：1. 固定 session 重跑 5 次；2. 对比每次检索的 top_k 与分数。

**处置**：分数在边界上接近时排序会抖。把 top_k 从 6 提到 8 或降低重排阈值。

**预防**：评测集里加「稳定性」子集，同题跑 3 次要求结果一致。


## R11　金额类答案小数点后位数不一

**现象**：金额类答案小数点后位数不一。

**排查**：1. 看 defaults.yml 的 decimal_places；2. 看模型是否在 SQL 里自带了 ROUND。

**处置**：统一由 defaults 注入 ROUND，禁止模型自己写 ROUND；已有 ROUND 的 SQL 在渲染层覆盖。

**预防**：输出约定进提示词 + 结果后处理双保险，加断言。


## R12　反馈里大量「答案对但结论错」

**现象**：反馈里大量「答案对但结论错」。

**排查**：1. 抽样看 trace；2. 看是否把相关当因果。

**处置**：这类不是 bug 是能力边界。在产品文案里明确「只给数据不给结论」，并调整示例。

**预防**：few-shot 里加入「不做因果推断」的反例。


## 通用原则

**先看 trace 再看日志**。日志告诉你"有没有报错"，trace 告诉你"哪一步慢了、哪一步返回了空"。
90% 的线上问题在 trace 的 span 树里一眼能看出来，翻日志反而更慢。

**能复现再动手**。所有入口都支持 `debug=true`，它会返回完整的检索证据、生成的 SQL、
校验结果和判定理由。拿到这四样，绝大多数问题不用猜。

**不要在高峰期改配置**。热重载是原子的，但重载后第一次查询会走冷路径（缓存未命中），
耗时可能是平时的 3 倍。改配置选在低峰，或者改完立刻跑一次预热查询。
