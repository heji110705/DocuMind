# DocuMind 系统评估（2026-11-12）

> 这份评估只写**能被复现或核对**的结论。每个数字都标了出处；
> 拿不到证据的地方写"未验证"，不写"应该没问题"。

---

## 0. 一句话结论

**功能交付是完整的，工程质量高于同类作品，但"90%"这个对外数字站不住，且成本列有可信度问题。**

- 该做的功能基本都做了（引用回链、拒答、多轮、增量索引、多租户、OCR、录屏），
  并且每一项都有实测数字，不是"实现了"三个字。
- 但核心指标经过两次扩张后从 90.4% 掉到 66.8%，掉的原因已归因清楚（检索预算，不是金标错）。
  继续对外说"90%"需要一个限定语，否则是过度陈述。
- 更需要注意的是：**README 里 `full` 那一行的 token / 调用次数与受控重测差近 2 倍**，
  这意味着成本列跨行不可比。这一条比准确率掉点更值得先修——因为它影响的是"数字可信"这个立身之本。

## 3. 已知缺陷

按"该先修哪个"排序，不按严重程度排序。

### 3.1 【最该先修】成本列跨行不可比

同一个 `full` 配置，两种测法差近 2 倍：

| 测法 | 调用/题 | token/题 | ¥/题 |
|---|---|---|---|
| 发布表（`data/eval_prod.json`） | 3.4（最多 6 次） | **11,461** | ¥0.0128 |
| 受控重测（同题、并发 3、缓存热） | 2.0 | **7,200** | ¥0.0074 |

再对照同一次受控测量里三组并列的结果：

| 配置 | 调用/题 | token/题 | ¥/题 |
|---|---|---|---|
| naive | 1.00 | 3,558 | ¥0.00405 |
| mix | 1.00 | 3,547 | ¥0.00407 |
| mix_guard | 1.83 | 6,460 | ¥0.00727 |

**原因有三层，逐层叠加：**

1. **LLM 响应缓存**。LightRAG 把关键词抽取结果缓存在 `kv_store_llm_response_cache.json`。
   发布表里 `mix` 的 124 道题**全部只有 1 次调用** —— 说明抽取 100% 命中缓存。
   冷启动实测是 2 次调用、4,383 token，比发布值（3,353）高 31%。
2. **`full` 那一轮是修复并发计量之前测的**。README §15.1 自己写过旧账本会让
   "单题成本虚高 2.4 倍"；11,461 / 7,200 ≈ 1.6，和这个量级吻合。
3. **不同组在不同缓存状态下测**，所以 `mix`(3,353) → `mix_guard`(5,461) → `mix_rr`(6,784)
   → `full`(11,461) 这个梯度里，既有真实差异（判定确实+80%），也有测量条件差异。

**影响**：准确率列仍然可信（同一轮里横向比），但**成本列不能跨行比较，也不能当报价**。
README 里"成本恒等而不是估算"那句话对 `mix_rr`/`full` 两行不成立。

**修法**：跑一次 `--no-cache`（清空或旁路 llm_response_cache）的五组全量，
把冷/热两种口径都报出来；或者在每行标注 cache hit 率。

### 3.2 【已修】三个"测试全绿但系统不能工作"

| 问题 | 表现 | 根因 |
|---|---|---|
| `JUDGE_PROMPT` / `evidence_block` 漏导入 | 快速与高精度都返回 `E2050` | 拆 `prompts.py` 时只导了"看起来会用到"的名字 |
| `Answer` 数据类整段丢失 | 每道题死在 `return Answer(...)` | 重写 `query.py` 时被 `Ingest` 覆盖 |
| `const drop` 与 `function drop` 重名 | 整个 ES 模块不执行，页面是静态壳 | `node --check` 按 CommonJS 解析，抓不到 |

三条都补了回归测试，且测试方式是"把那条路径真跑一遍"而不是加断言。

### 3.3 【已修】CI 的 unit job 会直接崩

`tests/test_answer_path.py` 会 `import query`，而 `query.py` 在模块级 import lightrag；
但 `unit` job 只装 `requirements-fast.txt`（不含 lightrag）→ 整批 collection error。

已修：`pytest.importorskip("lightrag")` + 让 `full` job 跑全量（否则那条用例永远被跳过）。
**但这两处都还没在 GitHub 上实跑过**，是这个修复目前唯一的缺口。

### 3.4 结构缺陷（未修）

| # | 缺陷 | 量化影响 |
|---|---|---|
| 1 | **判定器重复吃整份证据** | judge 3,621 tok 只为输出 3 个 token；占带判定总成本的 **49%** |
| 2 | **证据无压缩、无预算裁剪** | 6 块 × 972 字 ≈ 5,835 字 ≈ 3,560 tok，占作答提示词的 **98%** |
| 3 | **切块有 13.6% 重叠** | `chunk_chars` 114,523 vs `chars` 100,842；命中相邻块时重复付费 |
| 4 | **重排在并发下退化** | 3 个请求共享 `threads=4`，单题延迟约等于独占的 3 倍（实测 ~104s vs 22s） |
| 5 | **前端只有静态检查** | 没有浏览器级测试；本次那个"整个前端是死的"的 bug 就是静态检查的盲区 |
| 6 | **多租户索引要手工建** | 新租户第一次请求会报"索引不存在"，没有自动初始化流程 |
| 7 | **配额与密钥在进程内存** | 重启归零；明文比对；无轮换、无审计 |
| 8 | **Docker 从未构建** | 三个已知风险点（`libgomp1`、CJK 字体、非 root 挂载权限）全是推测 |

### 3.5 风险（不是 bug，但会被追问）

1. **16GB 内存是硬约束**：评测时可用内存只剩 1.5GB，重排组速率掉到 1.7 题/分钟，
   316 题的重排两组因此没跑完。这不是代码问题，但它让"数字齐全"这件事做不到。
2. **`chunk_top_k=6` 总会返回 6 块**：即使相关性很低也填满。
   好处是拒答确实由判定器负责（不是零证据早退，已验证 30/30 都有 6 块）；
   坏处是无证据时也要为 6 块无关文本付 token。
3. **单轮 vs 多轮的评测不可合并**：判定方式不同，合并会互相污染（已在 `run_eval_mt.py` 里分开）。

## 4. Token 消耗为什么高

### 4.1 实测拆分（工具：`tools/diag_tokens.py`）

对同一道题（"渠道 ROI 的分子是哪个字段？"）逐次记录每次 LLM 调用：

**不判定（mix，冷启动）**

| 步骤 | 输入 | 输出 | 耗时 | 占比 |
|---|---|---|---|---|
| 关键词抽取 | 648 | 33 | 1.7s | 15.5% |
| 作答 | 3,625 | 77 | 0.9s | 84.5% |
| **合计** | **4,273** | **110** | | 4,383 tok / ¥0.00504 |

**加判定（mix + guard）**

| 步骤 | 输入 | 输出 | 占比 |
|---|---|---|---|
| judge 证据判定 | 3,600 | 21 | 49.2% |
| answer 作答 | 3,644 | 94 | 50.8% |
| **合计** | **7,244** | **115** | 7,359 tok / ¥0.00824 |

**带多轮（历史 + 指代消解）**：rewrite 只用 159 in / 5 out = **164 tok（4.5%）**。
这一步设计得对，可以忽略成本。

### 4.2 四个原因，按贡献排序

1. **证据块全量入提示词（占 81%）**
   6 块 × 972 字中位数 = 5,835 字 ≈ 3,560 token，而 `SYSTEM_PROMPT` 只有 267 字。
   也就是说**作答提示词 98% 是原文**，没有摘要、没有句子级裁剪、没有 token 预算。
2. **判定器把同一份证据再吃一遍（+80%）**
   judge 的提示词 = 269 字模板 + 完整证据块。它输出一个 3 token 的判定词，
   却要付 3,600 token 的输入费。这是**最不划算的一笔开销**。
3. **关键词抽取是固定税（15%）**
   LightRAG 的抽取模板 648 token/次，与问题长度无关，每题都交。
   它的输出只有 33 token（几个关键词）。
4. **块间重叠 13.6%**
   命中相邻两块时，重叠部分被付两次钱。

### 4.3 输入/输出比 47:1 意味着什么

`3,625 : 77`。这是典型的"读多写少"，但它说明一件事：
**这套系统的成本由"喂进去多少上下文"决定，而不是由"生成多少字"决定。**
所以降本的正确方向是**减少/压缩上下文**，而不是限制作答长度
（后者省的是 ¥4.29/M 的输出，只占成本 9%）。

## 5. 与 InsightPilot 对比

两个项目都是"中文自然语言 → 结构化答案"，但任务形态不同，
**所以下面的对比只说工程取舍，不说谁更准。**

### 5.1 同口径数据

| | DocuMind（文档问答） | InsightPilot（自助问数） |
|---|---|---|
| 任务 | 6 块文档 → 一段带引用的答案 | 语义层 → SQL → 执行 → 统计选图 → 自检 |
| Python | 9,211 行 | 11,665 行 |
| 前端 | 544 行（8 模块，无构建） | 1,099 行 |
| 测试 | 128 条 | 267 条 |
| 评测集 | 124 题（另有 316 题扩题） | 60 题（6 类各 10） |
| 判定方式 | 关键词命中（组间 AND / 组内 OR） | **结果集等价**（列数/行序不比，1e-6 容差） |
| 主指标 | 可答率 90.4%（124 题）/ 66.8%（316 题） | EX 50.0% / 覆盖一致 57.5% |
| 模型调用 | 1.0–1.8 次/题 | **2.97 次/题** |
| token/题 | 3,550（不判定）/ 6,460（判定） | 4,867 |
| **单次调用平均 token** | **≈3,550**（作答调用） | **≈1,640** |
| ¥/题 | ¥0.0041 / ¥0.0073 | ¥0.00523 |
| p50 | 1.1 s / 21.8 s（重排） | 5.7 s |

### 5.2 三条实质差距

**① 上下文效率：差 2.2 倍**

DocuMind 的**作答调用一次塞 3,550 token**（另有一次 681 token 的关键词抽取）；
InsightPilot 平均每次调用 1,640 token。
原因不是模型不同，是**传的东西不同**：

- InsightPilot 传的是**压缩过的语义层**（表卡片 + 指标口径 + 范例 SQL），
  而且有显式的 `budget` 参数做预算裁剪（`app/semantic/retriever.py` 里
  `if used + cost <= budget` 逐项装填，装不下就丢）。
- DocuMind 传的是**6 块原文**，没有预算、没有裁剪、没有优先级。

这一条决定了两个系统的成本曲线形状：InsightPilot 增加一个 Agent 的边际成本低（每次调用便宜），
DocuMind 增加一块证据的边际成本高（每块 ~600 token）。
**DocuMind 之所以要用重排，部分原因就是上下文太贵、必须选得准。**
如果上下文便宜，多召回几块直接喂进去就行。

**② 评测可信度：InsightPilot 更硬**

InsightPilot 的分析维度是 DocuMind 缺的：

| 做法 | InsightPilot | DocuMind |
|---|---|---|
| 判定严格度 | 结果集等价（同一份数据必须算出同样的值） | 关键词命中（说了对的词就算对） |
| 重复性检验 | 有（`docs/03b`，同配置两轮极差 3–4pp） | 无 |
| 评测集审计 | 有（`docs/06`） | 有归因（`diag_misses.py`），无审计 |
| 规则基线对照 | 有（18.3%，用来证"模型确实在干活"） | 无 |
| 噪声带声明 | 有（"5pp 只比 3.4pp 噪声大一点，不说显著"） | 有（"<2pp 不写成结论"） |

**DocuMind 缺的是"重复性检验"**：同一个配置跑两轮，可答率会抖多少？
这个问题现在没有答案。而 124 题上 90.4% vs 89.4% 只差 1 道题——
如果重复性抖动有 3pp，这 1 道题的差异根本不该写进论文式的结论里。

**③ 产品完成度：InsightPilot 更接近"能交付"**

| | InsightPilot | DocuMind |
|---|---|---|
| 零配置可跑（无 Key） | 有（`IP_LLM_MODE=stub`，界面/SSE/trace/评测全部可用） | 无，没 Key 起不来 |
| 可观测性 | trace 落 SQLite + 树形可视化（每个节点的耗时与依据） | SSE 阶段事件 + 日志，无持久化 |
| 对外接口 | MCP stdio server（可被别的 Agent 调用） | HTTP + SSE |
| 自检脚本 | `scripts/doctor.py`（依赖/数据/语义层/Key 一次查完） | `check_requirements.py`（只管依赖） |
| 任务入口 | `python scripts/tasks.py demo/test/eval` 统一 | 散在多个命令里 |

**DocuMind 占优的地方**：

- 引用回链做到"点开即见原文段落"，InsightPilot 展示的是 SQL 和结果表，没有"出处段落"这个概念；
- 拒答有专门的判定环节，InsightPilot 的做法是 `out_of_scope → clarify`（回问用户），
  两者取舍不同，但 DocuMind 的"说不知道"更直接；
- 前端更轻（544 行 vs 1,099 行），无构建，clone 即开；
- 演示材料更完整（71 秒成片 + 逐段讲解稿 + 追问预案）。

### 5.3 一个必须说清的不可比点

**90.4% 和 50.0% 不能放在一起比。**

- DocuMind 的判定是"答案里出现了金标关键词"——模型说"高 28%"和"高 1.28 倍"算两个结果；
- InsightPilot 的判定是"SQL 跑出来的结果集和金标准等价"——列多一列就不算 EX。

后者严格得多。**如果 DocuMind 换成结果集等价判定，90.4% 会显著下降；
如果 InsightPilot 换成关键词命中，50% 会显著上升。**
拿这两个数字互相论证"我的方案更好"是不成立的，写进简历时也要分开写。

## 6. 可落地的改进（按投入产出排序）

### P0：直接影响"数字可信"

| # | 动作 | 预期收益 | 成本 |
|---|---|---|---|
| 1 | **重跑五组并关掉 LLM 缓存**（`llm_response_cache` 旁路），冷/热两套口径都报 | 成本列变得可比；预计 `full` 从 ¥0.0128 修正到 ¥0.0074 | 半天 + ¥5 |
| 2 | **做一次重复性检验**：同一配置跑两轮，报极差 | 补上最大的方法论缺口；预计抖动 3–5pp，能直接判定"90.4 vs 89.4"是否该写 | 2 小时 |
| 3 | **CI 真正跑一次**（push 到 GitHub 看两个 job） | 把"写了 CI"变成"CI 是绿的" | 20 分钟 |

### P1：降本（都有实测依据）

| # | 动作 | 预期收益 | 风险 |
|---|---|---|---|
| 4 | **判定与作答合并成一次调用**：一次调用同时输出「摘录+判定+答案」，判 INSUFFICIENT 就丢弃答案 | **省 ~45% token**（judge 的 3,600 完全消失） | 需要一个 few-shot 约束输出格式；可能略掉精度 |
| 5 | **证据按句/段检索**：先用块做粗排，再只把命中块里最相关的 2–3 句送进提示词 | 预计省 50–60%（3,560 → ~1,500） | 需要句子级相似度，实现成本中等 |
| 6 | **给证据加预算**：`EVIDENCE_BUDGET` 参数，按 token 装填、装不下就丢尾块 | 与 5 类似但更简单，能直接复用 InsightPilot 的思路 | 丢块可能掉召回，需 A/B |
| 7 | **关键词抽取降本**：换成更短的抽取提示词，或对短问题跳过抽取直接向量检索 | 省 ~650 tok/题（15%） | 检索质量可能略降 |

> 4+5 叠加后，带判定的单题成本可以从 6,460 降到约 2,500 token（**-61%**），
> 且不影响"答案必须来自证据"这个前提。

### P2：工程完整性

| # | 动作 | 说明 |
|---|---|---|
| 8 | **用 GitHub Actions 构建 Docker** | 本机没有 daemon，但 CI 有。这一步能绕开唯一的硬件限制，把"未验证"变成"已验证" |
| 9 | **加一条 Playwright 冒烟** | 只测"页面加载后徽标非空、能问一句、出现引用"三件事，防住本次那种"整个前端是死的" |
| 10 | **重排按并发自适应** | `threads = min(4, cpu//并发)` 或对重排加信号量；当前 3 并发下退化 3 倍 |
| 11 | **租户索引自动初始化** | 新租户首次请求时按需建索引，否则多租户这条路在真实使用里第一步就断 |
| 12 | **补 `doctor.py` 式的自检** | 依赖/索引/Key/端口一次查完，替代现在的"报错了再翻日志" |

### P3：可以不做但值得知道

- **8 秒延迟**：在 512 字 × 32 候选的前提下做不到。要么换 GPU（不是这个项目的目标），
  要么接受"高精度模式就是 20 秒，并且界面已经显示秒表和中止按钮"。
  继续在这条路上调参是负收益。
- **316 题的重排两组**：要跑得动需要先解决内存（关掉游戏进程能多出 2.5GB，
  实测速率能从 1.7 题/分钟回到 3 题/分钟，仍要 100 分钟）。
  它不是"没做"，是"这台机器做不完"，如实标注即可。

---

## 7. 总体判断

**能达到预期目标吗？**

- 作为**作品集项目**：**能，而且偏上**。功能闭环、有实测、有诚实的负结论
  （切块改造失败、判定为负收益、8 秒做不到都被写下来了），
  这些恰恰是面试时最能证明"真的做过"的部分。
- 作为**可交付的产品**：**不能**。缺 Docker 验证、缺持久化配额、缺零配置可跑、
  缺浏览器级测试，而且成本列现在不可信。距离 InsightPilot 那种"clone 下来三条命令跑通"还有明确差距。
- 作为**方法论示范**：**能**，但差最后一块——**没有重复性检验**。
  这是它和 InsightPilot 最本质的差距：后者敢写"5pp 只比噪声大一点，所以不说显著"，
  前者还没有量化自己的噪声带。

**如果只能做三件事：**
1. 重跑五组、关缓存、出冷启动成本表（修掉不可比的成本列）；
2. 做一次重复性检验（给所有准确率结论加上误差棒）；
3. 用 CI 构建 Docker（把唯一的"未验证"消掉）。

这三件事都不需要新的功能开发，但能把"看起来做完了"变成"经得起追问"。
